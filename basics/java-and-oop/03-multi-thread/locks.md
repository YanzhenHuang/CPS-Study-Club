# Java 各种锁详细讲解 + 全方位区别对比
Java 中的锁并不是单一分类，而是**从不同维度**划分的（比如竞争态度、公平性、重入性、共享性、锁升级等）。下面按**分类维度**逐一详细讲解，并把核心区别、底层实现、适用场景讲透，这也是面试最高频的锁考点。

---

## 先明确：锁的核心分类维度
1. 按**线程竞争态度**：悲观锁 / 乐观锁
2. 按**获取锁的顺序**：公平锁 / 非公平锁
3. 按**能否重复加锁**：可重入锁 / 不可重入锁
4. 按**锁的持有权限**：独占锁（排他锁）/ 共享锁（读锁）
5. 按**线程等待方式**：自旋锁 / 阻塞锁
6. 按 **synchronized 锁升级**：偏向锁 / 轻量级锁 / 重量级锁
7. 特殊功能锁：读写锁、分段锁、StampedLock、锁粗化/消除

---

# 一、悲观锁 vs 乐观锁（最核心的思想区别）
## 1. 悲观锁（Pessimistic Lock）
### 定义
默认认为**多线程一定会发生并发冲突**，所以在操作共享资源前，**先加锁，再执行**，确保同一时间只有一个线程操作资源。

### 底层实现
- `synchronized`
- `ReentrantLock`
- `ReentrantReadWriteLock` 的写锁

### 核心特点
- 加锁阻塞，线程竞争时会进入阻塞状态
- 绝对保证线程安全，不会出现数据错乱
- 线程阻塞/唤醒需要CPU上下文切换，开销大

### 适用场景
**写多读少、并发冲突严重**的场景，必须强一致性。

---

## 2. 乐观锁（Optimistic Lock）
### 定义
默认认为**并发冲突概率极低**，不加锁直接操作资源，操作完成后**校验是否被修改**，修改失败则重试。

### 底层实现
- **CAS（Compare And Swap）比较并交换**
- JUC 原子类：`AtomicInteger`、`AtomicLong` 等

### 核心特点
- 无锁设计，无线程阻塞、无CPU上下文切换
- 靠**自旋（循环重试）**保证操作成功
- 存在 **ABA 问题**，需用版本号（`AtomicStampedReference`）解决

### 适用场景
**读多写少、并发冲突低**的场景，性能远超悲观锁。

---

## 3. 核心区别总结
| 对比项 | 悲观锁 | 乐观锁 |
|--------|--------|--------|
| 核心思想 | 先防冲突，再操作 | 先操作，后校验 |
| 实现方式 | 加锁阻塞（synchronized/Lock） | CAS自旋 |
| 性能 | 冲突高时稳定，冲突低时开销大 | 冲突低时极快，冲突高时空耗CPU |
| 线程状态 | 阻塞/唤醒 | 一直运行（自旋） |
| 数据安全 | 强一致性 | 最终一致性 |

---

# 二、公平锁 vs 非公平锁（按获取锁的顺序）
## 1. 公平锁（Fair Lock）
### 定义
线程按照**申请锁的先后顺序**排队获取锁，先到先得，不允许插队。

### 实现
`new ReentrantLock(true)`

### 特点
- 无线程饥饿，所有线程都能拿到锁
- 需维护等待队列，**吞吐量更低**，性能差
- 底层基于 AQS 有序队列

---

## 2. 非公平锁（Non-Fair Lock）
### 定义
线程获取锁时**可以直接插队尝试**，不用排队，抢到就执行，抢不到再排队。

### 实现
- `synchronized`（默认非公平，不可修改）
- `new ReentrantLock(false)`（默认）

### 特点
- 吞吐量高，性能更好
- 可能出现**线程饥饿**（部分线程一直抢不到锁）
- 是生产环境默认选择

---

## 3. 核心区别总结
| 对比项 | 公平锁 | 非公平锁 |
|--------|--------|----------|
| 获取顺序 | 严格按申请顺序 | 允许插队 |
| 吞吐量 | 低 | 高 |
| 线程饥饿 | 无 | 可能出现 |
| 实现成本 | 高（维护队列） | 低 |
| 默认使用 | 否 | 是 |

---

# 三、可重入锁 vs 不可重入锁（按能否重复加锁）
## 1. 可重入锁（Reentrant Lock）
### 定义
**同一线程**可以**多次获取同一把锁**，不会自己锁死自己。
底层会维护一个**锁计数器**，加锁+1，解锁-1，为0时释放锁。

### 实现
- `synchronized`
- `ReentrantLock`

### 场景示例
```java
// 同步方法嵌套，可重入锁不会死锁
public synchronized void a() { b(); }
public synchronized void b() { }
```

---

## 2. 不可重入锁
### 定义
同一线程第一次获取锁后，再次尝试获取会**直接阻塞**，容易造成死锁。

### 实现
自定义简单锁（未做重入计数），Java 原生无内置不可重入锁。

---

## 3. 核心区别总结
| 对比项 | 可重入锁 | 不可重入锁 |
|--------|----------|------------|
| 重复加锁 | 允许，计数器+1 | 阻塞 |
| 死锁风险 | 低 | 极高 |
| 原生支持 | synchronized、ReentrantLock | 无 |
| 用途 | 生产必备 | 几乎不用 |

---

# 四、独占锁 vs 共享锁（按锁的持有权限）
## 1. 独占锁（排他锁 / 写锁）
### 定义
同一时间**只能有一个线程**持有锁，其他线程必须等待。
写操作必须独占，防止并发写导致数据错乱。

### 实现
- `synchronized`
- `ReentrantLock`
- `ReentrantReadWriteLock.WriteLock`

---

## 2. 共享锁（读锁）
### 定义
同一时间**多个线程可以同时持有读锁**，只允许并发读，不允许写。

### 实现
`ReentrantReadWriteLock.ReadLock`

### 规则
- 读锁 + 读锁 = 兼容（共享）
- 读锁 + 写锁 = 互斥
- 写锁 + 写锁 = 互斥

---

## 3. 核心区别总结
| 对比项 | 独占锁 | 共享锁 |
|--------|--------|--------|
| 持有线程数 | 1个 | 多个 |
| 操作类型 | 写操作 | 读操作 |
| 互斥性 | 全互斥 | 读读不互斥，读写/写写互斥 |
| 性能 | 低 | 读场景极高 |

---

# 五、自旋锁 vs 阻塞锁（按线程等待方式）
## 1. 自旋锁
### 定义
线程获取锁失败时，**不进入阻塞状态**，而是循环（自旋）不断尝试获取锁，直到成功。

### 实现
- CAS 底层
- 轻量级锁
- `Atomic` 原子类

### 特点
- 避免线程阻塞/唤醒的**上下文切换开销**
- 自旋会消耗CPU，并发冲突高时不适合

---

## 2. 阻塞锁
### 定义
线程获取锁失败时，直接进入**BLOCKED阻塞状态**，释放CPU，等待唤醒。

### 实现
- 重量级锁（synchronized 升级后）
- 传统互斥锁

### 特点
- 不消耗CPU，但上下文切换开销大
- 适合锁持有时间长、竞争激烈的场景

---

## 3. 核心区别总结
| 对比项 | 自旋锁 | 阻塞锁 |
|--------|--------|--------|
| 线程状态 | 运行态（自旋） | 阻塞态 |
| CPU消耗 | 高（自旋） | 低 |
| 切换开销 | 无 | 大（上下文切换） |
| 适用场景 | 锁持有时间短 | 锁持有时间长 |

---

# 六、偏向锁 / 轻量级锁 / 重量级锁（synchronized 锁升级）
这是 JDK1.6 对 `synchronized` 的核心优化，**锁只能升级，不能降级**，逐级适应并发竞争程度。

## 1. 偏向锁（Biased Lock）
- 适用：**无多线程竞争**，只有一个线程反复加锁
- 原理：锁对象标记当前线程ID，该线程再次加锁无需任何同步操作
- 特点：开销最低，几乎无性能损耗

## 2. 轻量级锁（Lightweight Lock）
- 适用：**少量线程竞争，锁持有时间短**
- 原理：取消偏向，线程通过**CAS自旋**尝试获取锁
- 特点：无阻塞，靠自旋竞争，避免上下文切换

## 3. 重量级锁（Heavyweight Lock）
- 适用：**竞争激烈，锁持有时间长**
- 原理：升级为操作系统互斥锁（Mutex Lock），线程阻塞
- 特点：性能最差，线程阻塞唤醒开销极大

## 升级流程
**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**

---

# 七、特殊功能锁（高频面试）
## 1. 读写锁（ReentrantReadWriteLock）
- 组合锁：**读锁共享 + 写锁独占**
- 规则：读读并发、读写互斥、写写互斥
- 场景：**读多写少**（缓存、配置读取），性能远超普通独占锁

## 2. StampedLock
- 读写锁的升级版，支持**乐观读**
- 无锁读，性能比 ReadWriteLock 更高
- 缺点：不可重入，编程复杂

## 3. 分段锁
- 原理：把数据分成多段，每段一把独立锁
- 实现：JDK1.7 `ConcurrentHashMap`
- 优势：减小锁粒度，提升并发效率

## 4. 锁消除
JVM 即时编译（JIT）检测到代码**无共享资源竞争**，直接删除锁代码（无意义的锁）。

## 5. 锁粗化
JVM 将**多次连续的加锁/解锁**合并为一次加锁，减少频繁加锁解锁的开销。

# 八、终极汇总：Java 常用锁实现类全维度对比
| 锁实现 | 悲观/乐观 | 公平性 | 可重入 | 独占/共享 | 锁类型 | 核心优势 |
|--------|-----------|--------|--------|-----------|--------|----------|
| synchronized | 悲观 | 非公平 | 是 | 独占 | 偏向→轻量→重量 | 简单、JVM自动管理 |
| ReentrantLock | 悲观 | 可选 | 是 | 独占 | 阻塞/自旋 | 灵活、可中断、可超时 |
| ReentrantReadWriteLock | 悲观 | 可选 | 是 | 读共享/写独占 | 阻塞 | 读多写少场景性能极高 |
| StampedLock | 悲观+乐观 | 非公平 | 否 | 读共享/写独占 | 乐观读 | 读性能最强 |
| CAS原子类 | 乐观 | 非公平 | 否 | 独占 | 自旋 | 无锁、高并发读场景极致性能 |

---

# 九、一句话记住核心区别
1. **悲观锁**加锁阻塞保安全，**乐观锁**无锁自旋拼性能；
2. **非公平锁**吞吐高，**公平锁**不饥饿；
3. **可重入锁**防自己死锁，**不可重入锁**基本不用；
4. **独占锁**保证写安全，**共享锁**提升读效率；
5. **自旋锁**省切换开销，**阻塞锁**省CPU资源；
6. **synchronized**自动锁升级，**Lock**手动控制更灵活。
